# 设计裁定 · 重复灵兽蛋计数规则（ENG-2）

> **项目**：《深窟兽语 / Hollowkin》
> **负责人**：文策渊（设计）+ 主理人裁定
> **版本**：v1.0（ENG-2 裁定）
> **关联**：架构文档 §1.3（Pouch）/ §7 ENG-2、`spirit-pouch-gdd.md` §6.4、`mvp-spirit-bestiary.md` v1.3 §0.1

---

## 0. 问题
玩家再次获得已拥有的灵兽蛋（同 species）时，背包如何处置？
- **方案 A**：`+1` 堆叠计数（同一 species 一条记录，`count` 字段 +1）
- **方案 B**：独立格占用（每颗蛋占一个独立格子）

该选择影响 Pouch 数据模型（计数 vs 独立实体）、序列化结构、UI 栏位压力，以及重复利用机制（升星 / 分解 / 喂养）的入口形态。

---

## 1. 候选方案对比

| 维度 | A · +1 计数 | B · 独立格 |
|---|---|---|
| 收集进度显示 | 单条显"已持有 N 只"，图鉴进度清晰 | 多个相同缩略图，进度需聚合计算 |
| 重复利用机制 | 天然提供"多只 → 升星 / 分解 / 喂养"计数入口 | 需先按 species 聚合再操作，链路更长 |
| 存档体积 / 读档复杂度 | 低：每 species 一行 + `count`（契合 ADR-1 极小存档） | 高：每颗蛋一行，重复获取迅速膨胀存档 |
| 单手触屏 UX | 栏位压力小，灵兽栏不易溢出 | 重复蛋占格，挤占异种展示空间 |
| 与现有架构对齐 | 架构 §1.3 已默认"同 species 标记 +1 计数" | 需改 Pouch 数据结构，偏离现行约定 |

---

## 2. 裁定结论
**采纳方案 A：`+1` 堆叠计数**。

理由：
1. 与架构文档 §1.3（Pouch）现行默认一致，**零返工**；
2. 单手触屏下显著降低栏位压力（MVP 灵兽栏仅 4 物种 + 后续 5–8，独立格在重复获取后迅速溢出）；
3. 为升星 / 分解 / 喂养等重复利用机制提供现成计数入口；
4. 存档极小（ADR-1 原则）更契合——同 species 多只仅增一个 int。

---

## 3. 数据模型影响（落点：Pouch）

- `spirit_entry.gd`：灵兽条目结构增加 `count: int`（默认 1）；species 为键，重复获取 `count += 1`，**不新增条目**。
- 序列化：`save_run.cfg` / 元进度中灵兽栏以 `{slug: count}` 映射存储，非逐蛋展开。
- 图鉴解锁：以"是否首次获得（`count` 由 0 → ≥1）"触发解锁，与计数解耦。

---

## 4. 接口契约（本次不改代码，供 Pouch 实现遵循）

- `Pouch.add_spirit_egg(slug: String) -> void`：已存在则 `entry.count += 1`，否则新建 `count = 1`。
- `Pouch.get_spirit_count(slug: String) -> int`：返回该 species 持有数。
- 升星 / 分解 / 喂养接口以 `count` 为输入，不依赖逐蛋实体。

---

## 5. 待决点
若后续引入"个体养成差异"（如每只独立等级 / 性格），方案 A 的扁平计数需升级为"物种聚合 + 个体列表"二级结构；当前 MVP 不引入，裁定以方案 A 为基线，预留 `count` → `instances:[]` 的演进路径。
